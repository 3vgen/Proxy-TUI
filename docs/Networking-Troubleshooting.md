# Сеть: грабли и решения (ЧИТАТЬ ПЕРЕД РАБОТОЙ)

Самая дорогая часть проекта — отладка сети TUN. Эти четыре пункта уже «горели», не наступи на них снова.

## 1. UFW режет ответы через tun0 (главный грабли) ⚠️
**Симптом:** sing-box active, tun0 поднят, ip rules на месте, но любой TCP через тун висит (curl `000`/timeout), при этом запросы sing-box-собственные (DoH-DNS) работают.

**Причина:** на хосте **UFW active с INPUT policy drop**. Ответы на соединения, идущие через tun0, приходят как «новые» пакеты на INPUT (не conntrack-established из-за особенностей пути через tun) → молчаливый drop.

**Решение (сделано):**
```bash
sudo ufw allow in on tun0 comment "sing-box tun"
```
Правило сейчас в UFW (`Anywhere on tun0 ALLOW`) — удалять его нельзя, иначе VPN перестанет отвечать.

**Диагностика:** если TCP через тун снова молчит — сначала проверить `ufw status | grep tun0`.

## 2. self-loop: трафик sing-box к своим же узлам заворачивается в tun
**Симптом:** узел по `nc/bash /dev/tcp` недоступен, хотя напрямую (без TUN) всё работает; tcpdump показывает 0 пакетов к узлу.

**Причина:** auto_route кладёт весь трафик в таблицу 2022 (через tun). Собственные сокеты sing-box к Reality-серверу попадают в свой же тун.

**Решение (сделано):** в конфиге tun inbound обязательно
`route_exclude_address: ["<ip узла>/32", ...]` для **каждого** узла.
CLI делает это автоматически в `build_global_config()` (резолвит hostname в IP).

## 3. DNS в sing-box 1.12+/1.14 — только новый формат
**Симптом:** `decode config … legacy DNS server formats are deprecated in 1.12 and removed in 1.14`.

**Решение:** устаревший формат (`"address": "https://1.1.1.1/dns-query"`) не работает. Правильно:
```json
"dns": { "servers": [ { "type": "https", "server": "1.1.1.1", "tag": "dn" } ] }
```
Также: **без DNS-сервера в конфиге** перехваченные tun DNS-запросы никто не отвечает → всё «молчит» и в логе тысячи `inbound DNS packet`. Если удаляешь DNS-блок — не удивляйся.

## 4. Reality-объект — внутри tls, а не сбоку
В конфигурации VLESS outbound поле reality **вложено в tls**. Ошибка `json: unknown field "reality"` = поставил не туда. См. [[Subscription-Nodes]].

## 5. «Симптомы-обманки» при тестировании
- Несколько sing-box одновременно → конфликт порта socks `10880`/`1080`, «всё 000». Перед тестами: `pkill -f 'sing-box run'`.
- Список узлов меняется от загрузки к загрузке — всегда сверяй индекс с актуальным `list`.
- `handshake_ms = 1` у половины узлов — это **не** значит, что узел туннелирует. Реальная проверка только `test <n>` (реальный egress через прокси). Узлы `201.34.132.43:*` дают 1 ms, но мёртвые.
- Egress РФ у части узлов (даже если «заграничные» имена) — бесполезен для OpenAI/Anthropic.

## 6. stop/start безопасны, но помни
- `systemctl stop sing-box` полностью снимает tun и правила — прямой интернет возвращается (проверено).
- Конфиг генерится из live-файла `/etc/sing-box/config.json` как базы; если руками сломал конфиг и сервис не стартует — `systemctl stop` и чини `/etc/sing-box/config.json` либо откат `configs/singbox-last.json`.

## 7. Открытый вопрос
- При некоторых DNS-запросах через DoH 1.1.1.1 возвращались подозрительные A (напр. api.ipify.org → `8.47.69.0`) — источник не выяснен, но на работу не влияет (ipify не критичен). Если будет повторяться с реальными доменами — копать в сторону ответов DoH/прозрачного перехвата у провайдера.

## 8. Входящий SSH ломается при включённом VPN на сервере (асимметричный маршрут) ⚠️
**Симптом:** `ssh homeserver` виснет/таймаутит, когда VPN на сервере **включён**, а на
клиенте (Mac) — **выключен**. При выключенном VPN на сервере или включённом на обоих
сторонах — работает.

**Причина (асимметричная маршрутизация):** `auto_route` кладёт **весь** не-private
и не-узловой трафик в таблицу `2022` (через tun0). Ответы на **входящие** SSH-соединения
уходят в тун с IP VPN-узла, а не обратно через роутер. Клиент получает SYN-ACK от
чужого IP → рукопожатие не завершается.

Почему «при включённом VPN на обоих» работало: exit-IP VPN на Mac совпадал с одним
из узлов подписки (напр. `5.129.218.70` = узел #4), а IP узлов исключены из туна
(`route_exclude_address`) → ответы шли напрямую случайно. С реального IP провайдера
(не-узел) ответы уходят в тун — и всё ломается.

**Решение (сделано):** маркировка входящих SSH-соединений и policy-routing ответов
мимо туна:
- nftables: `tcp dport 22 → ct mark 0x1` (prerouting), затем `ct mark 0x1 → meta mark 0x1` (output).
- ip rule: `8500: fwmark 0x1 lookup main` (pref < 9000, поэтому выигрывает у sing-box).
- Всё оформлено скриптом `~/vpn-tool/ssh-bypass.sh` + systemd-юнитом `vpn-ssh-bypass.service` (переживает ребут и `vpn use`/restart sing-box).

```bash
sudo ~/vpn-tool/ssh-bypass.sh status       # проверить правило и таблицу
sudo ~/vpn-tool/ssh-bypass.sh install      # поставить заново
# проверка маршрута:
ip route get 8.8.8.8 mark 0x1             # должно идти dev wlp1s0 (прямо)
ip route get 8.8.8.8                      # должно идти dev tun0 (в тун)
```

**Диагностика:** если входящий SSH снова не работает при активном VPN — проверить
`ip rule | grep 8500` и `nft list table inet vpn_ssh_bypass`, затем `systemctl status vpn-ssh-bypass`.
